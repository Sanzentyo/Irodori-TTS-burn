# RTX 5070 Ti Laptop 12 GiB: v4 priority 1--4 report (2026-08-21)

## 結論

優先度1--4の実装とfresh計測を完了した。今回の主要結果は次の通りである。

1. F16 all-resident E2Eは、6長さ × 3 voice × 5 fresh WGPU sessionと、6長さ ×
   5 fresh Python sessionを取り直した。各sessionは2 warmup + 10 measuredである。
   WGPUはdevice-complete/readback-completeとも18条件中11条件でPyTorch F16より短かった。
   ただし事前に固定したF16複合accuracy gateを通したのは11/18で、速度とaccuracyの両方を
   通したのは7/18に留まる。従ってF16をproduction defaultへ昇格しない。
2. F16 RFは、手書きWGSLのF32 scalar accumulator projectionを避け、Burn/CubeK matmulへ
   dtype別にrouteする。旧routeとのscreenでは112/489/685 framesのRFが2.41×/2.80×/2.52×に
   なった。F32は従来routeを維持する。
3. RF safetensors loaderはheaderとoffsetを一度だけ検証するportable indexed readerをdefaultにした。
   5 fresh sessionでRF checkpoint loadは5.634秒から5.265秒へ6.55%、all-resident load wallは
   6.238秒から5.902秒へ5.39%短縮した。音声hashとlive GPU bytesは不変である。
4. `PhaseBatch`へ真のhomogeneous tensor batchを追加した。N=12、45 frames、同一話者では
   逐次RFに対してRF phase wallを63.72%、全phase execution wallを33.72%短縮し、throughputを
   50.85%改善した。persistent in-useは不変、reserved/NVMLは約96/105 MiB増えた。

性能だけで見ると改善は大きいが、accuracy failureを速度PASSとして扱わない。特に489-frame
text-onlyはSNR 33.18 dBでもmax abs 0.1653でFAILであり、既知の長尺accuracy懸念は解消済みではない。

## 比較境界とRF意味論

- device-complete: pre-start device syncからRFとcodecそれぞれのdevice completionまで。表は両stageの和。
- readback-complete: 上記にowned contiguous CPU F32 audio取得を加えた境界。file writeは計測外。
- consumer-complete: WGPU側のaudio hash consumer受理まで。PythonのCPU-ready wallと同一ではないので
  runtime比較の主表には使わない。
- first request: process-local shader/pipeline compileを含む。steadyへpoolしない。
- aggregation: 各fresh session内10 measuredのmedianを取り、5 sessionのmedianを報告する。

4 Euler evaluations、linear schedule bits
`[1065336439,1061146329,1056947831,1048559223,0]`、12 layers、48 block callsを
requestごとに照合した。text-onlyはforward batches `[2,2,1,1]`、effective rows 6である。
voice designとprepared cloneはcaption/speaker CFGがtext CFGから独立するため、実際の正しいtopologyは
`[3,3,1,1]`、effective rows 8だった。全voiceをrows 6とする旧runner assumptionはfail-closedに
停止し、schema 8で修正した。PythonとWGPUは同じsemantic workだがsame operator graphではない。

10.2秒と19.56秒はbinary floatの`seconds * 48000`をPython upstreamがfloorし、当初1 sample短い
結果を返した。このattemptは破棄した。Python harnessへ`--latent-frames`を追加し、255/489 framesを
exact 489,600/938,880 samplesとして全30 sessionを取り直した。比較時の全18条件はsample数が一致する。

## All-resident VRAM、load、warmup

12GB all-residentは全6長さ・3 voiceでOOMなしに成立した。最長685-frame cloneの実測は次の通り。

| runtime / metric | persistent/idle | request/allocator peak | NVML process peak |
|---|---:|---:|---:|
| WGPU in-use / reserved | 2,392.8 / 2,399.0 MiB | reserved 4,435.5 MiB | **4,706 MiB** |
| PyTorch allocated / reserved | 1,809.1 / 3,708 MiB | allocated 3,338.3 / reserved 5,586 MiB | 5,804 MiB |

Rust allocator値とPyTorch allocator値は同じ定義ではないため、persistent差を直接「何MiB多い」とは
断定しない。外部NVMLでは最長条件のWGPU peakがPythonより1,098 MiB低かった。

全条件のload wall中央値はWGPU 6.188秒、PyTorch 4.864秒で、WGPUが約1.324秒遅い。
indexed loader採用A/Bは以下である。

| RF loader | RF checkpoint | all-resident load wall | audio hash | RF live bytes |
|---|---:|---:|---|---:|
| Burn Store | 5.634 s | 6.238 s | `6e0953ac…` | 1,532,104,832 |
| indexed file | **5.265 s** | **5.902 s** | `6e0953ac…` | 1,532,104,832 |

indexed loaderはsafe `File::seek/read_exact`だけを使い、Vulkan/Metal/DX12共通である。unsafe mmapや
NVIDIA専用APIへ依存しない。header/offset/dtype/shapeを一度検証し、Burnのkey remapとdtype castは
従来どおり適用する。

CubeCL persistent cacheをrestoreしても、WGPU fresh processのfirst consumerは短尺で7.21--7.36秒、
685 framesで8.51--9.23秒だった。Python first readbackは同条件で約0.09--0.54秒である。CubeCL DBは
autotune selectionと一部compiler artifactを再利用するが、process-local WGPU pipeline objectと
手書きWGSL driver compileを消さない。cross-platformな本命はlong-lived sessionとreadiness前warmupで
あり、Vulkan限定pipeline cacheは補助策に留める。

## F16 RF projection route

489-frame profileではMLP expand/contractとQKV projectionが支配的で、F16 storageを毎scalar F32で
積算する手書きWGSLはtensor-capable CubeK matmulを活かせていなかった。dtypeをroute keyへ含め、
F16だけBurn/CubeKへ戻し、F32は既存手書きrouteを維持した。

| frames | 旧手書きRF | F16 CubeK RF | 短縮 | 旧routeとのwaveform SNR |
|---:|---:|---:|---:|---:|
| 112 | 106.97 ms | **44.36 ms** | 58.52% / 2.41× | 38.31 dB |
| 489 | 302.74 ms | **108.14 ms** | 64.28% / 2.80× | 39.88 dB |
| 685 | 419.91 ms | **166.45 ms** | 60.36% / 2.52× | 37.33 dB |

これはadapter固有のtile parameter調整ではなく、precisionと実装familyを正しく対応させる構造変更で
ある。profile用の`IRODORI_DISABLE_DIT_PROJECTION`はA/Bだけで、production F16 routeは環境変数に
依存しない。

## True tensor micro-batch

`PhaseBatch<RfResident -> LatentsResident -> CodecResident -> Complete>`のtypestateを維持したまま、
`sample_homogeneous_tensor_batch`を追加した。全requestのprepared tensorsをbatch axisで結合し、
RFを一回実行後、latent viewをGPU residentのまま個別itemへ戻す。geometry、CFG topology、dtype、shapeが
一致しないbatchはdispatch前に拒否する。

| N=12 / 45 frames | sequential | homogeneous tensor | 差 |
|---|---:|---:|---:|
| RF actual device sum | 525.58 ms | **135.84 ms** | -74.15% / 3.87× |
| RF phase wall | 591.54 ms | **214.59 ms** | -63.72% |
| complete phase wall | 1,118.73 ms | **741.57 ms** | -33.72% |
| requests/s | 10.73 | **16.18** | +50.85% |
| audio-seconds/wall-second | 19.31 | **29.13** | +50.85% |
| RF warm persistent in-use | 2,316,344,960 B | 2,316,344,960 B | unchanged |
| RF warm reserved | 2,332,307,264 B | 2,433,075,008 B | +96.1 MiB |
| NVML peak median | 2,395 MiB | 2,500 MiB | +105 MiB |

逐次とtensor batchは異なるmatmul reduction/orderを選ぶためbitwise hashは異なるが、直接比較は
max abs 0.015625、RMSE 0.001146、SNR 42.22 dB、cosine 0.999970でF16 gateを通った。
latentは全件codecまでGPU residentで、final audio以外をCPU readbackしていない。

## Crate ergonomics

- `ModelCheckpointLoader::{BurnStore, IndexedFile}`でhost materialization policyをenum化した。
  defaultは`IndexedFile`で、明示A/Bも同じAPIから行える。
- `PhaseBatch`の既存typestateを壊さず、homogeneous batchだけを明示methodとして追加した。
  request単位の`Option`組合せではなく、batch admissionを一箇所でfail-closedにする。
- runnerの`RfBatching::{Sequential, HomogeneousTensor}`はpolicyとreportを一致させる。
- Python比較も`--latent-frames`を追加し、float secondsによるinvalid paired stateを排除した。
- text/design/cloneのCFG topologyをruntime manifestから検証し、report schema 8へ反映した。

production crateとしては、`RuntimeBuilder<Cold> -> OnlineSession<Ready>`へwarmup manifest、cache receipt、
prepared speakerをまとめる高水準APIがまだ不足する。今回の低水準primitiveやloader choiceをcallerへ
漏らさず、session builderへ集約するのが次のergonomics改善である。

## 次の優先順位

1. 7つのF16 accuracy FAILをlatent/RF/codecへ二分し、最初のdivergenceを層別に保存する。特に489-textを
   解消するまで長尺F16をaccuracy-approvedにしない。
2. auxiliary CFGのB3 projection/attentionを重点profileする。design/cloneでPythonに負ける条件は、
   text-only B2の勝ちを壊さず別routeとして改善する。
3. long-lived `OnlineSession<Ready>`とmanifest-driven real warmupをcrate APIへ昇格する。現在7--10秒の
   fresh-process first requestをservice requestへ露出させない。
4. indexed loader後もPythonよりloadが約1.32秒遅い。validated indexの再利用、host staging arena、
   bounded parallel uploadを別々にA/Bし、VRAM/host RAM peakを悪化させない案だけ採用する。
5. homogeneous tensor batchを同一長・同一CFGごとのgrouping schedulerへ一般化する。混在長をpadする案は
   semantic workが変わるため別campaignにする。
6. WGPU timestamp対応がportableに利用できるadapterでは、host sync wallに加えてGPU timestampを保存する。

Python F16はPyTorch wheel同梱CUDAを使うため、system CUDAを混在させない。今回の親shellには
`LD_LIBRARY_PATH=/usr/local/cuda/...`があり、cu128 PyTorchへ別CUDAライブラリが混ざると全F16 GEMMが
`CUBLAS_STATUS_INVALID_VALUE`になった。final campaignは各processを
`env -u LD_LIBRARY_PATH CUDA_DEVICE_ORDER=PCI_BUS_ID CUDA_VISIBLE_DEVICES=0`で起動した。
これは失敗条件と原因を保存した上での環境修正で、失敗requestをretryして性能値を選んだものではない。
